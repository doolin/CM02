# Evidence Store Architecture

The S3 bucket `inventium-artifacts` serves as the **authoritative evidence store** for all CI/CD pipeline compliance artifacts. Under [OMB M-26-05](https://www.whitehouse.gov/wp-content/uploads/2026/01/M-26-05-Adopting-a-Risk-based-Approach-to-Software-and-Hardware-Security.pdf), agencies must validate software security through risk-based assessment using machine-readable evidence. This archive replaces implicit vendor trust with pipeline-produced, tamper-evident artifacts.

## Directory Structure

```
inventium-artifacts/
├── cm02/
│   ├── pdfs/                          # Generated assessment PDFs (ephemeral, 24h TTL)
│   │   └── 2026-04-17T21-30-00Z-<uuid>.pdf
│   ├── evidence/
│   │   ├── sboms/                     # CycloneDX SBOMs (PW.4)
│   │   │   └── 2026-04-17T21-30-00Z-<commit>-sbom-cyclonedx.json
│   │   ├── scans/                     # Vulnerability scan results (PW.7, PW.8)
│   │   │   ├── 2026-04-17T21-30-00Z-<commit>-npm-audit-results.json
│   │   │   └── 2026-04-17T21-30-00Z-<commit>-trivy-scan-results.json
│   │   ├── provenance/               # Build provenance attestations (PS.1, PS.2)
│   │   │   └── 2026-04-17T21-30-00Z-<commit>-provenance.json
│   │   ├── oscal/                     # OSCAL-formatted artifacts (future, WS4)
│   │   │   └── 2026-04-17T21-30-00Z-<commit>-assessment-results.json
│   │   └── logs/                      # Pipeline audit logs (future, WS3)
│   │       └── 2026-04-17T21-30-00Z-<commit>-pipeline-log.json
│   └── access-logs/                   # S3 access audit trail
└── ...
```

## Naming Convention

All evidence artifacts follow the pattern:

```
cm02/evidence/<type>/<timestamp>-<commit-prefix>-<artifact-name>.<ext>
```

- **timestamp**: ISO 8601, colons replaced with hyphens for S3 compatibility
- **commit-prefix**: first 12 characters of the Git commit SHA
- **artifact-name**: descriptive name matching the artifact type
- **ext**: `json` for structured evidence, `pdf` for assessment documents

## Retention Policy

| Artifact Class                             | Retention             | Storage Tiering                    | Rationale                                   |
| ------------------------------------------ | --------------------- | ---------------------------------- | ------------------------------------------- |
| Evidence (SBOMs, scans, provenance, OSCAL) | 3 years (Object Lock) | Standard → IA (90d) → Glacier (1y) | NARA guidance for system security records   |
| Assessment PDFs                            | 24 hours              | Standard                           | Ephemeral; user downloads via presigned URL |
| Access logs                                | 3 years (Object Lock) | Standard → IA (90d) → Glacier (1y) | Audit trail for evidence integrity          |

## Artifact Metadata

Every object uploaded to the evidence store includes S3 object metadata:

| Key                | Description                                            |
| ------------------ | ------------------------------------------------------ |
| `artifact-type`    | Category: `sbom`, `scan`, `provenance`, `oscal`, `log` |
| `sha256-digest`    | SHA-256 hash of the artifact content                   |
| `upload-timestamp` | ISO 8601 timestamp of upload                           |
| `commit`           | Full Git commit SHA (CI/CD uploads only)               |
| `run-id`           | GitHub Actions run ID (CI/CD uploads only)             |

## Relationship to M-26-05

M-26-05 rescinds mandatory vendor attestation (M-22-18, M-23-16) in favor of agency-led, risk-based validation. FSA's posture:

1. **Evidence is pipeline-produced** — every artifact is generated by the CI/CD pipeline itself, not self-reported by vendors
2. **Evidence is tamper-evident** — SHA-256 checksums and Object Lock prevent modification after upload
3. **Evidence is machine-readable** — JSON-formatted artifacts support automated verification and OSCAL ingestion
4. **Evidence is queryable** — S3 prefix structure and metadata enable programmatic audit queries

This archive is the foundation for continuous verification: compliance posture can be assessed at any time by querying the evidence store, without requesting attestations from vendors or personnel.

## Terraform Requirements (form-terra)

The following changes must be applied to the `inventium-artifacts` bucket in the [form-terra](https://github.com/daviddoolin/form-terra) repository:

- [ ] Enable S3 Object Lock in compliance mode with 1095-day (3-year) default retention
- [ ] Verify bucket versioning is enabled
- [ ] Enable server-side encryption with AWS KMS and bucket key
- [ ] Enable S3 access logging to `access-logs/` prefix (same bucket or dedicated log bucket)
- [ ] Block all public access (`block_public_acls`, `block_public_policy`, `ignore_public_acls`, `restrict_public_buckets`)
- [ ] Add lifecycle rules: evidence (`cm02/evidence/`) transitions to Standard-IA at 90 days, Glacier at 1 year; PDFs (`cm02/pdfs/`) expire at 1 day
- [ ] Add IAM policy for CI/CD evidence writer role: `s3:PutObject`, `s3:PutObjectTagging`, `s3:GetObject` on `cm02/*`

**Note:** Object Lock must be enabled at bucket creation time. If the existing bucket does not have Object Lock enabled, a new bucket will be required.
